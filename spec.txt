1. Vision & Philosophy
tpt-invariant is a lightweight, zero-FFI, native Rust formal verifier. It is designed to be the "ripgrep" of the verification ecosystem: blazing fast, trivial to install via cargo install, and deeply integrated into the Rust workflow.
The Rust Advantage: Unlike C/C++ verifiers (like Kani/CBMC), tpt-invariant does not verify memory safety, data races, or thread safety. Rust’s borrow checker and type system already guarantee these. tpt-invariant exclusively verifies logical correctness (arithmetic, bounds, state transitions, and user-defined contracts). This shrinks the verification state space by orders of magnitude.
The "Gated Unbounded" Philosophy: We reject the binary choice between "fast but incomplete" (Bounded) and "slow but complete" (Unbounded). tpt-invariant uses a 3-tier gating system to provide unbounded proofs when possible, and gracefully degrades to bounded proofs when math gets too complex, ensuring the tool never hangs.
2. The Backend: The "Rust Z3" (tpt-solver)
tpt-invariant relies entirely on tpt-solver. To support this tool, tpt-solver will evolve from a pure QF_LRA engine into a full DPLL(T) SMT Solver tailored specifically for Rust's discrete math.
tpt-invariant requires tpt-solver to provide:
CDCL SAT Engine: To resolve the boolean skeleton of Rust's control flow (&&, ||, !).
QF_LIA (Linear Integer Arithmetic): To handle exact integer bounds (i32, usize) without the false positives of real-number rounding.
QF_BV (Bitvectors): To perfectly model Rust's exact 32-bit/64-bit integer overflow, wrapping, and bitwise operations.
Note: tpt-invariant is completely agnostic to how tpt-solver implements these internally, as long as it accepts constraints and returns SAT/UNSAT with counterexamples.
3. Architecture: The 4-Stage Pipeline
Stage 1: Contract Ingestion (Frontend)
Users write contracts using procedural macros. This avoids custom syntax parsing and integrates natively with cargo.

use tpt_invariant::contracts;

#[requires(x > 0 && y > 0)]
#[ensures(result >= x && result >= y)]
fn max(x: i32, y: i32) -> i32 {
    if x > y { x } else { y }
}

Implementation: The tpt-invariant-macros crate parses these strings into an internal AST at compile time.
Stage 2: IR Extraction & CFG Generation
To maintain fast compile times and avoid nightly rustc_driver dependencies for the MVP:
AST/CFG Extraction: Uses the syn crate to parse the function body and build a simplified Control Flow Graph (CFG).
Desugaring: Converts Rust constructs (match, for, while) into a simplified, SSA-like (Static Single Assignment) intermediate representation.
(Note: V2 will transition to parsing Rust MIR directly for 100% fidelity, but AST/CFG is the pragmatic solo-maintainer MVP path).
Stage 3: Symbolic Execution & The "Gate"
The engine walks the CFG, replacing concrete variables with Symbolic Expressions. It accumulates Path Conditions (the boolean logic required to reach a specific point). When it hits an assert!, an array index, or an ensures block, it generates a Verification Condition (VC).
The 3-Tier Gated Unbounded Engine:
Instead of blindly unrolling loops or hanging on complex math, the engine applies the Gate:

Stage 4: Solving & Reporting
The VC and Path Conditions are translated into tpt-solver constraints.
To prove correctness, tpt-invariant asks tpt-solver: "Is there any assignment where Path Conditions are TRUE, but the VC is FALSE?"
If UNSAT: Code is proven correct.
If SAT: tpt-solver returns a Counterexample (e.g., "Fails when x = -5"), which tpt-invariant formats into actionable terminal output.
4. Crate Specifications & Workspace Structure
tpt-invariant is a Cargo Workspace containing three distinct crates to keep compile times fast and dependencies clean.

tpt-invariant/
├── Cargo.toml                 # Workspace root
├── crates/
│   ├── tpt-invariant-macros/  # Proc-macros (#[requires], #[ensures])
│   │   ├── Cargo.toml
│   │   └── src/lib.rs
│   ├── tpt-invariant-core/    # The engine (CFG, Symbolic Exec, The Gate)
│   │   ├── Cargo.toml
│   │   └── src/
│   │       ├── lib.rs
│   │       ├── cfg.rs         # Control Flow Graph generation
│   │       ├── symbolic.rs    # Symbolic execution & k-induction gate
│   │       └── solver.rs      # tpt-solver integration
│   └── tpt-invariant-cli/     # The binary (`cargo invariant`)

Dependency Graph

5. CLI Interface
The user interacts with the tool via standard cargo commands. The "Gate" is exposed via simple flags.

# Default behavior: Bounded up to 50. Fast, incomplete.
cargo invariant check 

# Gated Unbounded: Tries bounded, then attempts k-induction with a 2s timeout gate.
cargo invariant check --prove 

# Strict Mode: If the unbounded gate trips, fail the CI pipeline.
cargo invariant check --prove --strict

# Custom Bound: Override the default bounded limit.
cargo invariant check --bound 100

6. Scope & Boundaries (What it DOES NOT do)
To remain viable for a solo maintainer and keep the tool lightweight, tpt-invariant explicitly does not handle:
Memory Safety / UB: Handled by the Rust compiler.
Concurrency / Thread Safety: Handled by the Rust compiler and tools like Loom.
Non-Linear Arithmetic: (e.g., x * y < 10 where both are variables). Handled by bounding or falling back to Tier 3.
External FFI / System Calls: Treated as uninterpreted functions (black boxes) that return arbitrary valid values.
